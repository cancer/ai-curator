# AI curator — 仕様定義

`docs/01_requirements.md` の要件を、パイプライン各段の入出力と振る舞いに落とす。

根拠の出典表記: `(BS L*)` は `docs/ai_curator_brainstorm.md` の行番号、URL は公式ドキュメントを指す。
数値パラメータ（重み・閾値・頻度の具体値）は未確定であり、`【暫定】` と明記した値は PoC・実運用で調整する (BS L114)。

## 1. パイプライン全体

```
[Sources] → Fetch/Ingest → Normalize → Dedup/Score → Store → フィード構築 → Deliver
```

6 段パイプライン。安い処理（機械的 Dedup）を先に置き、意味的処理へ渡す前に件数を減らす (BS L11-18)。

**実行は 1 日 1 回の単一パスに統合する**（2026-07-09 改定。従来の「高頻度 Fetch 系 + 日次 Digest 系」の 2 系統分離 (BS L106) は廃止）:

| 実行 | 頻度 | 処理 |
|---|---|---|
| 日次パス | 1 日 1 回 | Fetch（当日分を全件・ページング）→ Normalize → 機械的 Dedup → Store（メタ）→ Embedding → 意味的 Dedup → Score → 全件要約・傾向サマリ → Store（派生物）|

- 単一パスにできる理由: 原文を保存しない（§10）ため、取得したテキストを同一パス内でメモリのまま埋め込み・要約に使い回せる。系統を分けて中間状態を持つ必要がない
- 各ソースは**当日ウィンドウ内を全件取得**する（先頭 N 件で打ち切らずページングする。「すべて」が要件）

## 2. ソース仕様（2026-07-09 改定）

汎用フィードを主軸にし、フィードで代替できない構造化 API のみ専用ソースとして残す。改訂前の 4 系統固定（GitHub / HN / Medium / Fowler）(BS L55-63) は PoC の「性質の異なる代表を 1 本ずつ」試すサンプルであり、Medium・Fowler は汎用フィードに統合した。

| ソース | 取得方式 | エンドポイント | 本文抽出 |
|---|---|---|---|
| 汎用フィード（主軸） | RSS/Atom | ユーザー設定の任意フィード URL（例: `https://medium.com/feed/@{author}`, `https://martinfowler.com/feed.atom`） | item/entry の `content:encoded` → `content` → `description` の優先順で本文を取り、いずれも無ければリンク先を取得し粗いタグ除去（root/exclude なしの HTML→テキスト）。取得失敗時はスニペット→タイトルにフォールバック |
| GitHub Releases | REST API | `GET /repos/{owner}/{repo}/releases`（https://docs.github.com/en/rest/releases/releases） | 不要（release note が本文） |
| Hacker News | Algolia API | `https://hn.algolia.com/api/v1/search_by_date`（https://hn.algolia.com/api） | リンク先の外部ページを取得し粗いタグ除去で本文化（任意サイトで個別抽出は書かない。取得失敗時は story_text/タイトルにフォールバック） |

- 監視対象（フィード URL・リポジトリの具体リスト）はユーザー設定とし、コードから分離する（§7・設計 §6.1）
- 汎用フィードは「フィード提供の本文（`content:encoded`/`content`/`description`）があればそれを使い、無ければリンク先を粗いタグ除去で本文化」に統一する。かつては Medium=テンプレ抽出・Fowler=記事ページ `<main>` 個別抽出と分けていたが、要件 FR-2 のとおりヘッダ等のノイズは Embedding 時に関連度が低く埋もれるため、任意フィードには粗いタグ除去で足りる。全ソースで抽出条件を揃える必要はない（比較可能性が要求するのは同一 Embedding モデルだけで、ノイズ量ではない）(BS L62)

## 3. 正規化スキーマ

全ソースの出力を以下の共通形式に揃える。保存可否は法務方針 (BS L74-77) に従う。

| フィールド | 内容 | 永続化 |
|---|---|---|
| `url` | 正規化済み URL（トラッキングパラメータ除去） | ○ |
| `title` | タイトル | ○ |
| `source` | 媒体名・ソース種別 | ○ |
| `published_at` | 公開日時 | ○ |
| `feed_summary` | フィード提供の要約/スニペット | **×（原文由来のため非永続。取得時にメモリで埋め込みに使い破棄）(2026-07-09 改定)** |
| `body` | 抽出本文 | ×（処理中のみメモリ、破棄）(BS L76) |
| `content_hash` | タイトル+フィード提供テキストのハッシュ（SimHash 用） | ○ |

冪等キーは正規化 URL or コンテンツハッシュの unique 制約【暫定: 正規化 URL】。確定は PoC 後 (BS L113)。

## 4. Dedup 仕様

2 段階で実施する (BS L23-25)。

1. **機械的 Dedup**（日次パス前半・保存前）
   - SimHash/MinHash により完全重複・ほぼ重複を除去
   - LLM・Embedding を使わない（コスト 0 に近い）
2. **意味的 Dedup**（日次パス後半・Embedding 後）
   - cosine 類似が閾値【暫定: 0.9】以上の記事をクラスタ化
   - クラスタごとに代表 1 本を選出【暫定: ソース信頼度が高く公開日時が新しいもの】

## 5. Embedding 仕様

- Workers AI の bge 系モデルを使用（トークン課金・原文非保持）(BS L24)
- モデル候補は**多言語モデルに限定**する（確定 2026-07-06 ユーザー判断）。理由: 日本語ソース導入を見込むため、英語特化モデルの採用は将来のベクトル空間分裂（異モデル間で cosine 比較不能）か全件再 Embedding を強制する
  - `@cf/baai/bge-m3`: 多言語・context window 60,000 トークン・最安（$0.012/M input tokens）。第一候補【暫定】
  - `@cf/qwen/qwen3-embedding-0.6b`: 多言語（提供元 Qwen の説明。Cloudflare ページに明記なし、検証③で日本語動作を確認）・context window 8,192 トークン・同額（$0.012/M input tokens）。代替候補
  - 各モデルページ: https://developers.cloudflare.com/workers-ai/models/
- 記事の Embedding 入力: **タイトル + フィード提供テキスト**（title-summary 方式。PoC 実測で本文全文を足してもランキングはほぼ変わらないため本文は使わない）。フィード提供テキストは保存せず、取得時にメモリで埋め込み計算に使って破棄する
- 関心軸の Embedding 入力: **ラベルから LLM が生成した関心記述文**（2026-07-09 改定。§6.2・§7）。ユーザーはラベルしか与えないので、日次パスの軸同期でラベルから記述文を生成し、それを記事と同一の Embedding モデルでベクトル化する。生成記述文は自前生成物だが保存不要（埋め込みに使って破棄し、ベクトル＋ラベルのハッシュ＋モデル名のみ永続化する）
- ベクトルは原文復元不可のため永続化できる (BS L77)。読み出し時は生成モデル名が一致するベクトルのみ比較に使う（記事側・関心軸側とも同一モデルの空間でのみ cosine 比較する）

## 6. スコアリング仕様

### 6.1 スコア式 (BS L26)

```
score = 関心類似 × w1 + 鮮度 × w2 + ソース信頼度 × w3
```

- 重み w1〜w3 は未確定。PoC は「上位が読む価値ある順に見えるか」の目視確認まで (BS L91-95)

### 6.2 関心類似 — 複数ベクトル方式（確定）(BS L42-47)

- 関心プロファイルは関心軸ごとに独立したベクトルを持つ。既定は 4 軸（Web フレームワーク / AI / Agentic Coding / Software Designing）で、設定画面から追加・削除できる（軸数は固定ではない）
- 各軸ベクトルは、ユーザーが与えたラベルから LLM で関心記述文を生成し、それを Embedding して得る（2026-07-09 改定。§5・§7）。ユーザーが入力するのはラベルだけで、記述文の手書きは廃止
- `関心類似 = max(記事ベクトルと各関心軸ベクトルの cosine)`（OR 的判定）
- 最大値を与えた軸を「ヒット軸」として記録し、digest の選定理由に使う (BS L47)

### 6.3 鮮度・ソース信頼度

- 鮮度: 公開日時からの経過時間による減衰【暫定: 指数減衰】
- ソース信頼度: ソースごとの固定値【暫定】。種別ごとの重み分岐は実運用フェーズ (BS L100)

## 7. 関心プロファイル仕様 (BS L36-40)

| 系統 | 内容 | フェーズ |
|---|---|---|
| 明示指定 | ユーザーはトピックのラベル（日本語可）だけを与える。日次パスの軸同期でラベルから LLM が関心記述文を生成し、それを Embedding して関心軸を構築（2026-07-09 改定。記述文の手書きは廃止） | v1 から |
| 暗黙学習（フィードバック） | 既読/評価を関心軸ベクトルへ還流して更新 | 実運用 |
| 明示ルール（フィルタ） | ドメイン単位の常時含む/除外 | 実運用 |

フィルターバブル対策の混合比率は未確定 (BS L114)。

## 8. フィード仕様

- 配信形態は YouTube ホームフィード型のランク付きフィード（確定 2026-07-07、FR-7）。上位で hard cut せず、全件をスコア順に並べ「もっと見る」で下位を順次読み込む
- ランキングの再生成頻度: 1 日 1 回 (BS L106)
- フィードは「当日傾向サマリ（§8.1）」＋「ランク付き記事リスト（§8.2）」で構成する

### 8.1 当日傾向サマリ（FR-6.1）

- 対象は当日母集団（機械的 Dedup 後の全記事）。フィードを 1 件ずつ辿らなくても全体傾向を俯瞰する
- **集計単位は関心軸（キュレーションのジャンル）**（確定 2026-07-07）。軸ごとにセクションを立てる構成
- 提示内容（暫定）:
  - 軸ごとのヒット件数（各記事のヒット軸 = `max(cosine)` を与えた軸で集計）
  - 軸内の意味的 Dedup クラスタから見た当日の主要トピック（大きいクラスタ = その軸で話題が集中した領域）
  - 上記を入力に LLM が軸ごとに 1〜2 文の日本語で傾向を叙述【暫定】
- 集計値・要約のみを扱い、個別記事の原文を含まない（§10 に抵触しない）
- 傾向サマリは当日限りの自前生成物。保存可否は §10 に従う（保存する場合は digest 本文の一部として）

### 8.2 ランク付き記事リスト

- 当日母集団を関連度スコア（§6）の降順で全件並べる。hard cut しない
- 「もっと見る」で下位を順次読み込む（ページング）。1 ページの件数は未確定【暫定: 20 件】
- 各項目の必須要素:
  - タイトル・媒体名・公開日時
  - 一次ソースへの URL リンク（必須。原文を持たない代わりの出典担保）(BS L80)
  - 選定理由（ヒットした関心軸）(BS L47)
  - 自前生成の要約（LLM 生成。保存可）(BS L75)
- **LLM 要約は全件生成する**（2026-07-09 確定）。日次パス内で全記事の本文を取得（汎用フィード=`content:encoded`/`content`/`description`、無ければリンク先を粗抽出 / GitHub=release note / HN=リンク先を粗抽出）して要約し、summaries テーブル（1 記事 1 行）に保存する。取得失敗はスニペット→タイトルにフォールバックし、1 件の失敗で全体を止めない
- 配信フォーマットの細部は未確定 (BS L115)

## 9. 配信仕様 (BS L78-79)

- アクセスは作成者本人のみ。Cloudflare Access 等の認証で保護する
- 公開 Pages 化・SNS 自動投稿は実装しない（公衆送信への非接触を設計で担保）

## 10. データ保存仕様（法務方針の固定）(BS L72-84)

- 保存 OK: URL / タイトル / 媒体名 / 日時 / content_hash / 自前生成の要約・傾向叙述 / ベクトル（+生成モデル名）
- 保存 NG: 他者の原文テキストの永続化。**本文だけでなくフィード提供の要約・スニペットも保存しない**（2026-07-09 改定。原文由来はすべて非永続。URL があれば再取得できるため保存不要）
- 実装上の帰結: 本文もフィード提供テキストもパイプライン処理中のみメモリに存在し、Embedding・要約生成に使った後に破棄する。永続化するのは派生物（ハッシュ・ベクトル・自前生成の要約）のみ

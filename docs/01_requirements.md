# AI curator — 要件定義

LLM の定期実行で Web 上から関連トピックを集めるパーソナル情報収集システムの要件を整理する。

根拠の出典表記: `(BS L*)` は `docs/ai_curator_brainstorm.md` の行番号、URL は公式ドキュメントを指す。

## 1. 背景・目的

- 主目的: 自分用の情報収集（パーソナルダッシュボード）(BS L7)
- 追う対象: 技術トレンド（ライブラリ/手法/リリース）、業界ニュース・時事 (BS L8)
- スタンス: 厳選重視。量より質、少数を選抜する (BS L9)

## 2. 利用者

- 単一ユーザー（作成者本人）のみ。共有・公開はしない (BS L78)

## 3. 機能要件

### FR-1 収集（Fetch/Ingest）

- 全ソースを Pull 型（RSS/API）で取得する。Twitter API はコスト不adopt (BS L51)
- 対象ソースは性質の異なる 4 系統から開始する (BS L55-60):
  - GitHub Releases（構造化 API・高信頼）
  - Hacker News（Algolia API・スコア付き・玉石混交）
  - Medium（著者/タグ feed・HTML 構造一定）
  - martinfowler.com/feed.atom（PF 非依存の個人ブログ代表・独自 HTML）
- fetch は高頻度で実行し、記事を貯める (BS L106)

### FR-2 正規化（Normalize）

- ソースごとに異なる形式を共通スキーマに正規化する (BS L14)
- 本文抽出は「テンプレ化できる PF」と「個別対応の独自サイト」の両方式を持つ (BS L62)

### FR-3 重複除去（Dedup）

- 機械的 Dedup: SimHash/MinHash で完全重複を LLM/Embedding なしで除去する (BS L23)
- 意味的 Dedup: Embedding の cosine 類似でクラスタ化し、同一話題を代表 1 本にまとめる (BS L25)

### FR-4 関連度スコアリング（Score）

- 各記事を Embedding でベクトル化する（Workers AI bge 系）(BS L24)
- `関心類似 × w1 + 鮮度 × w2 + ソース信頼度 × w3` の加重和で上位を選抜する (BS L26)
- 関心プロファイルは複数ベクトル方式。軸ごとに `max(各トピック cosine)` で OR 的に判定する (BS L42-46)

### FR-5 関心プロファイル管理

3 系統を併用する (BS L36-40):

1. 明示指定（シード）: 興味トピック/代表記事をベクトル化して初期構築
2. 暗黙学習（フィードバック）: 既読/評価を関心プロファイルに還流
3. 明示ルール（フィルタ）: ドメインの常時含む/除外で補正

### FR-6 Digest 生成

- LLM による digest 生成は 1 日 1 回に集約する (BS L18, L106)
- どの関心軸でヒットしたかを選定理由として表示する (BS L47)
- 出典は必ず一次ソースへの URL リンクで担保する (BS L80)

### FR-6.1 当日の記事傾向サマリ

- digest 冒頭に、その日に収集した記事全体（選抜前の母集団）の傾向を提示する（2026-07-07 追加）
- 目的: 厳選された少数の digest だけでは見えない「その日どの話題が多かったか」を俯瞰する。選抜からこぼれた領域の動きも把握できる
- 提示内容（暫定）: 関心軸ごとのヒット件数分布、意味的クラスタから見た当日の主要トピック、件数の多かったソース
- 傾向は当日母集団の集計・要約であり、個別記事の原文を含まない（NFR-2 に抵触しない）

### FR-7 配信（Deliver）

- 出力は完全非公開。自分だけがアクセスできる（Cloudflare Access 等で認証）(BS L78)
- 公開 Pages・SNS 自動投稿は行わない (BS L78-79)

## 4. 非機能要件

### NFR-1 コスト

- 安い処理を先に、高い処理を後に置き、LLM に渡る件数を段階的に絞る (BS L17)
- Fetch 層（高頻度・安価）と LLM 層（1 日 1 回集約）を分離する (BS L18)
- Embedding は Workers AI（Neurons 課金、無料枠 10,000 Neurons/日）を利用する
  （https://developers.cloudflare.com/workers-ai/platform/pricing/）

### NFR-2 法務・規約（安全側に固定）(BS L70-84)

- 保存は「メタ + 自前生成物 + ベクトル」のみ
  - 保存 OK: URL / タイトル / 媒体名 / 日時 / フィード提供の要約 / 自前生成の要約 / ベクトル
  - 保存 NG: 本文全文の原文永続化（処理中のみメモリで扱い破棄）
  - 保存 NG の対象は本文全文の複製のみ。要約は複製に当たらない整理であり（2026-07-06 ユーザー確認）、その保存可否は非公開方針とは独立。非公開 (BS L78) は出力を公衆送信に触れさせないための別個の決定
- 公衆送信に一切触れない（完全非公開）
- 出典 URL リンクを必須とする
- 許容する副作用: 本文非保存のため、モデル入替時の再 Embedding は再 fetch 頼み。記事消失時は再生成不可 (BS L83)

### NFR-3 技術基盤

- 既存スタック（Cloudflare Workers + Cron Triggers + Queues + D1 + Workers AI）を流用する (BS L19)

## 5. 制約・前提

- Twitter API は不採用（コスト・規約リスク）(BS L51)
- 関連度判定は PoC で完成させない。精度は実運用のフィードバックループで育てる (BS L32)
- 法務整理は法律家の見解ではなく安全側の一般整理。公開配信を本格化する場合は専門家確認が必要 (BS L84)

## 6. スコープ外（実運用フェーズに送る）(BS L98-100)

- 提唱者ホワイトリストの本格運用
- リンクグラフによる二次発見
- ソース種別ごとのスコア重み分岐

## 7. 未確定事項（PoC 後に確定）(BS L110-116)

- D1 スキーマの確定（ベクトルを D1 JSON/BLOB → 実運用で Vectorize 移行の段階方針）
- 冪等キー設計（正規化 URL or コンテンツハッシュの unique 制約）
- スコアの重み・閾値・フィルターバブル対策の混合比率
- 配信フォーマットの細部
- 技術構成の具体化

# AI curator — ブレスト結論まとめ

LLMの定期実行でWeb上から関連トピックを集める、パーソナル情報収集システム。

## 目的・スコープ

- **主目的**: 自分用の情報収集（パーソナルダッシュボード）
- **追う対象**: 技術トレンド（ライブラリ/手法/リリース）、業界ニュース・時事
- **スタンス**: 厳選重視（質優先・少数）

## アーキテクチャ（6段パイプライン）

```
[Sources] → Fetch/Ingest → Normalize → Dedup/Score → Store → Digest生成 → Deliver
```

- **安い処理を先に、高い処理を後に** 置き、LLMに渡る件数を段階的に絞る
- Fetch層（高頻度・安価）と LLM層（1日1回集約）を分離してコスト圧縮
- 既存スタック（Cloudflare Workers + Cron Triggers + Queues + D1 + Workers AI）を流用

### Dedup / Score の中身

1. **機械的 Dedup**（SimHash/MinHash）— LLMもEmbeddingも使わず完全重複を安く除去
2. **Embedding** — 各記事を意味ベクトル化（Workers AI bge系、トークン課金なし）
3. **意味的 Dedup**（cosine類似 → クラスタ化）— 文言が違うが同じ話題をまとめ代表1本に
4. **関連度 Scorer** — `関心類似 × w1 + 鮮度 × w2 + ソース信頼度 × w3` の加重和で上位を選抜

## 関連度スコアリング

- cosine類似度・ANN検索は**枯れた技術**（情報検索の古典、LLM以前から存在）。部品は既存実装に任せる
- 悩むのは**組み合わせ方とチューニング**（重み・閾値・何をEmbeddingするか）
- **関連度判定はPoCで完成しない**。PoCは「土台が壊れてない」確認まで。精度は実運用のフィードバックループで育てる

## キュレーションの方向性（関心プロファイル）

3系統を併用:

1. **明示指定（シード）** — 初期構築。興味トピック/代表記事をベクトル化
2. **暗黙学習（フィードバック）** — 既読/評価を関心プロファイルに還流して育てる
3. **明示ルール（フィルタ）** — ドメインの常時含む/除外で補正

### 単一ベクトル vs 複数ベクトル → 複数ベクトルで確定

- **単一ベクトル = AND的**（全興味を平均＝重心）。全軸に近い記事しか勝てず、興味が分散していると全部低スコアになる
- **複数ベクトル = OR的**（軸ごとに持ち `max(各トピックcosine)`）。どれか1軸に刺されば拾う
- 興味が「技術トレンド / 業界ニュース / デザイン論」と明確に別方向なので複数ベクトルが正しい
- 副次効果: 「どの軸でヒットしたか」を選定理由としてdigestに表示でき、信頼性が上がる

## ソース戦略

Twitter API は**コストが合わず不採用**。全ソースをPull型（RSS/API）で構成し、料金・規約リスクを回避。

### PoC ソース構成（性質の異なる代表を1本ずつ）

| ソース | 役割 |
|---|---|
| GitHub Releases | 構造化API・高信頼 |
| Hacker News (Algolia API) | スコア付き・玉石混交 |
| Medium（著者/タグ feed） | PF代表・HTML構造一定＝抽出テンプレ化可 |
| martinfowler.com/feed.atom | PF非依存の個人ブログ代表・独自HTML＝抽出は個別対応 |

- **本文抽出の両極**（テンプレ化できるPF vs 個別対応の独自サイト）をカバーし、抽出戦略を見極める
- Fowlerフィードは実在確認済み（`https://martinfowler.com/feed.atom`、Atom形式、本人がシンジケーション許可）

### 実運用での拡張

- ソフトウェアデザイン論は公式がなく提唱者個人ブログに散る → **提唱者ホワイトリスト**を一級ソース化
- Scorer の重みを**ソース種別ごとに変える**（高信頼な構造化ソースは軽め、玉石混交なブログ系は意味的スコアリングが主役）

## 法務・規約 → 安全側に確定

法的判断を設計から切り離すため、以下を固定する。

1. **保存は「メタ + 自前生成物 + ベクトル」のみ**
   - 保存OK: URL / タイトル / 媒体名 / 日時 / フィード提供の要約 / 自前生成の要約 / ベクトル
   - 保存NG: 本文全文の原文永続化（処理中だけメモリで扱い破棄）
   - ベクトルは原文復元不可なので複製にあたりにくい
2. **出力は完全非公開**（自分だけがアクセス、Cloudflare Access等で認証。公開Pages・SNS自動投稿はしない）
   - 「自分が読むため」でも公開投稿は私的利用を外れるため、公衆送信に一切触れない設計にする
3. **出典は必ずURLリンクで担保**（原文を持たない代わりに一次ソースへ飛ぶ）

- 得られるもの: 媒体ごとの規約を個別調査せずに済む、保存内容が自動的に決まる
- 副作用: 本文を保存しないためモデル入替時の再Embeddingは再fetch頼み（記事が消えていれば再生成不可）。パーソナル用途なら許容
- ※法律家の見解ではなく安全側の一般整理。公開配信を本格化する場合は要専門家確認

## PoCで検証すること

```
① GitHub / HN / RSS が安定取得できるか（軽い疎通確認）
② 本文抽出の両極（Medium=テンプレ / Fowler=個別）が機能するか
③ 抽出 → Embedding → 関連度スコアが「読む価値ある順」になるか目視
④ コスト実測（Workers AI Neurons / LLM digest 実トークン）
```

- 関連度は「上位がゴミだらけでない」程度で合格とし、過剰に作り込まない
- 最大の未検証リスクは**データをどこから取るか**（ソース確保）

### PoCでは不要（実運用フェーズ）

- ホワイトリストの本格運用、リンクグラフ二次発見、ソース種別ごとの重み分岐

## 今の確定事項 / 後回し

**確定**

- cron粒度: fetch=高頻度（貯める）／ digest=1日1回、の2系統分離
- 関心プロファイル: 複数ベクトル（本実装）
- 規約: 安全側（保存最小・非公開・出典URL）

**PoC後で良い**

- D1 schema のたたき台（ベクトルをD1 JSON/BLOB → 実運用でVectorize移行の段階方針）
- 冪等キー設計（正規化URL or コンテンツハッシュのunique制約）
- スコアの重み・閾値・フィルターバブル対策の混合比率
- 配信フォーマットの細部
- 技術構成の具体化
